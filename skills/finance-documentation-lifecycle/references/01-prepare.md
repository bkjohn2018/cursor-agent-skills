# Phase 1: Prepare – Plan & Risk Identify

**Goal**: Define the documentation need, scope, owner, audience, and compliance drivers *before* you start writing.

**ISO 9001 alignment**: Clause 6.1 (risk-based thinking) and 4.4 (determine processes needed). Poor preparation leads to documentation that doesn't meet user needs or compliance requirements.

---

## Steps

### 1. Define Purpose and Scope

**Ask**:
- What is this documentation for? (e.g., "Describe how we record revenue," "Guide staff through the close process," "Document the variance threshold for GL reconciliation")
- What process or procedure does it cover?
- What are the boundaries? (in scope, out of scope)
- Is this new documentation, or replacing/updating existing documentation?

**Document**:
- **Document Title**: Clear, searchable name (e.g., "Revenue Recognition SOP," not "Doc_v3")
- **Purpose Statement**: One-sentence reason this documentation exists
- **Scope**: What's included; what's not (reference related docs)
- **Effective Date**: When this documentation applies
- **Previous Version**: If replacing something, note the prior version and why it's being retired

---

### 2. Identify Owner and Audience

**Owner**:
- Who is responsible for keeping this documentation current?
- Who approves changes?
- Who answers user questions about this procedure?
- Document owner's name, title, contact

**Audience**:
- Who uses this documentation? (e.g., AR team, audit team, finance managers, data analysts)
- What's their level of financial/technical knowledge?
- What decisions or tasks do they perform with this documentation?
- Will they access it online, print it, reference it during training?
- What feedback channel will they use when the documentation is inaccurate, unclear, missing, or hard to use?

**Format implication**: If audience is senior executives, use high-level narrative. If audience is junior staff, use step-by-step instructions.

---

### 3. Identify Compliance and Risk Drivers

**Compliance**:
- Is this documentation required by regulation? (SOX, internal control framework, accounting standards)
- Is this required for audit readiness?
- Are there external requirements? (partner, customer, regulatory)
- Document the source (regulation, standard, policy, audit finding)

**Risk & Opportunity**:
- What could go wrong if this procedure is not documented? (errors, audit findings, noncompliance, inefficiency)
- What is the risk level? (high, medium, low) based on financial impact, audit exposure, frequency
- What opportunity exists? (streamlining, automation, cost reduction)

**Governance implication**: High-risk documentation needs more formal review, approval, and revision cadence. Low-risk reference documents can be lighter-weight.

---

### 4. Plan Customer Feedback and Nonconformity Handling

**Finance/accounting customer feedback**:
- Define how users will report questions, confusion, missing steps, broken links, outdated screenshots, or unclear terms.
- Identify who triages feedback, how quickly they respond, and where feedback evidence is retained.
- Decide whether feedback is handled informally, through a ticket queue, through a document owner mailbox, or through a registry field.

**Documentation nonconformities**:
- Define what counts as a nonconformity: inaccurate, outdated, missing, unclear, uncontrolled, inaccessible, unapproved, or not followed.
- Define when a nonconformity requires immediate containment, revision, escalation, or corrective action.
- Record where nonconformity logs, exception decisions, and corrective action evidence will be stored.

---

### 5. Plan Review and Approval Chain

**Who reviews**:
- Finance manager for accuracy
- Compliance/audit team for control design
- Subject matter expert (if not the owner)
- System owner (if documentation depends on a system)

**Who approves** (formal sign-off):
- Document owner
- Finance leader (CFO, Controller, VP Finance)
- Compliance/audit leader (if high-risk or required for audit)

**Timeline**:
- When does this need to be ready? (business need date)
- How long for review? (plan for 2–4 weeks for high-risk, 1 week for low-risk)
- How long for approval? (plan for 1–2 weeks)

---

### 6. Plan Storage, Access, and Retention

**Storage location**:
- Where will the authoritative copy live? (Sharepoint folder, Wiki page, GitHub wiki, internal knowledge base)
- How will users find it? (index, search, linked from process flow)
- How will you track versions? (version number, date, author in metadata)

**Access control**:
- Who can view? (all finance staff, select roles, public)
- Who can modify? (owner only, owner + manager, broader review group)
- Who can retire/delete? (owner + leader only)

**Retention**:
- How long to keep this version? (e.g., 3 years past supersession, 7 years per SOX)
- What happens when you retire it? (archive with retirement reason, delete after retention period)
- What evidence must be retained for review, approval, revision, retirement, and exception decisions?

---

### 7. Define Review Cadence

**Formal review schedule**:
- High-risk controls: annually or after process change
- Medium-risk: every 2 years or after change
- Low-risk reference: every 2–3 years or on-demand

**Trigger for unscheduled review**:
- Process redesign or system change
- Audit finding or control gap
- User question or documented variance
- Regulatory change
- Nonconformity or error traced to documentation weakness

---

## Preparation Checklist

Before you start writing, confirm:

- [ ] Purpose and scope clearly defined
- [ ] Owner identified (name, contact, authority)
- [ ] Audience identified (roles, knowledge level, use case)
- [ ] Compliance drivers documented (regulations, standards, policies)
- [ ] Risk level assessed (high/medium/low)
- [ ] Customer feedback channel and response owner defined
- [ ] Nonconformity handling route defined
- [ ] Approval chain defined
- [ ] Storage location identified
- [ ] Access control model defined
- [ ] Review cadence set
- [ ] Retention requirement understood
- [ ] Evidence retention location identified

---

## Common Pitfalls

| Pitfall | Why It Matters | How to Avoid |
|---|---|---|
| Unclear purpose | Documentation drifts; users unsure when/how to use it | Write a one-sentence purpose; get owner to approve |
| Wrong audience level | Too technical for users; too basic for experts; nobody reads it | Name your audience; ask 2–3 users to review draft for clarity |
| Missing compliance driver | Audit gaps; failure to demonstrate control design | List every regulation, policy, audit finding that drives this doc |
| No owner identified | Document goes stale; nobody answers questions; drifts out of sync with process | Name owner in metadata; set their review calendar; hold them accountable |
| No approval plan | Document is not official; users doubt its authority; changes made informally | Define who must approve before you start writing; build approval timeline |
| Storage location unclear | Users can't find it; multiple versions exist; confusion about what's current | Decide where NOW (Sharepoint, Wiki, etc.); add link to index/process page |

---

## Output: Preparation Summary

Once you've completed this phase, you should have:

1. **Document metadata sheet** (title, purpose, scope, owner, audience, version date)
2. **Risk and compliance drivers** (list of why this documentation exists)
3. **Approval plan** (who reviews, who approves, timeline)
4. **Customer feedback and nonconformity plan** (how issues are reported, triaged, corrected, and retained)
5. **Storage and access plan** (location, access control, version tracking)
6. **Review cadence and triggers** (schedule, what prompts unscheduled review)

Use these outputs to guide **Phase 2 (Structure)** and ensure your documentation team has a shared understanding of what's needed and why.
