Plan a dashboard webspace as a product surface before moving into page design or implementation.

Collect these inputs first:
- Product goal and business function
- Primary and secondary users
- Core decisions supported
- Screenshot, mockup, reference patterns, or design inspiration
- Entities/workflows to represent
- Candidate KPIs and operating signals
- Data sources and known data constraints
- Technology target and implementation scope

Execute by phase:

1. **Question and value framing**
   - Apply `question-driven-data-projects`.
   - Clarify business question, decision owner, success criteria, risks, and go/no-go boundaries.

2. **Product framing**
   - Apply `dashboard-product-framing`.
   - Define user roles, jobs to be done, monitoring vs action workflows, and success criteria.

3. **Content and object modeling**
   - Apply `governance-dashboard-content-model` when the dashboard includes governed objects, workflow stages, lineage, controls, issues, or evidence.
   - Identify summary objects, drill objects, statuses, and traceability paths.

4. **Information architecture**
   - Apply `dashboard-information-architecture`.
   - Define global nav, page map, section hierarchy, drill paths, and page responsibilities.

5. **Dashboard design direction**
   - Apply `finance-dashboard-design` when the webspace is finance-led, KPI-dense, or a governed operating dashboard.
   - Apply `analytics-storytelling` for narrative emphasis and visual clarity.
   - Define page hierarchy, narrative emphasis, and visualization approach.

Output must include:
1. Dashboard product brief
2. User/decision map
3. Page map and drill-path spec
4. Content model summary
5. Candidate KPI list
6. Open questions, assumptions, and next build step
